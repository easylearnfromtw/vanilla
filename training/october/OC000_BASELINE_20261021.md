## P0 阻擋與不相容（需在標示 M1 已驗收前解除）

### B-001：現有 Self-Build 手動 Draft PR 路徑與新決策的明確界線不同

- **觀察**：現有程式 `src/builder/autocode-client.ts` 具有瀏覽器 `createCodePR(patch)` 對 `/propose` 發 POST 的介面；`services/self-build-github-worker/index.mjs` 對此路由執行 `propose(body,env)`，建立 Draft PR；原有 `docs/SELF_BUILD_AUTONOMOUS_CODE.md` 更明確把聊天與 Self-Build CODE 工作台描述為可建立 PR 的入口。
- **衝突**：經正式 Q25/Q28/Q45/Q48/Q49/Q50，Self-Build 僅限可信後端排程或經驗證內部品質事件啟動，不能由普通使用者聊天、按鈕、Plugin、SDK 或外部事件直接／間接觸發。即使 `/propose` 只能建立 Draft PR、不可直接合併，仍不能將它視為**已符合 Self-Build 後端觸發政策**。
- **工程處置**：把既有明確由人工提出的「一般程式碼建議／手動 Draft PR」與受限 Self-Build 分為兩種**不同 task_type、身份、路由、事件 schema、權限及儲存稽核**。只有經可信後端事件信任根驗證的內部事件可觸發 Self-Build；手動程式碼開發如要繼續提供，須獨立命名且有真正的 Owner 後端操作許可與明確人工審核，絕不能被轉送至 Self-Build scheduler。普通 Browser 帶有獨立 Bearer 也不自動等於經驗證 Ceres Owner。
- **具體驗收**：在不修改真實 GitHub 的 Mock Worker／整合環境，以普通聊天、Telegram 按鈕、外部 API、SDK、README prompt injection、用戶排程與假內部事件做測試，**Self-Build enqueue 必須全部拒絕**；可信內部簽驗事件才能建立候選；高風險合併／部署另外要求本人 Ceres 對指定 digest/version/nonce 批准。
- **標記**：`severity=P0`、`status=open`、`verification=not_run`；不要因 GitHub 存在 Draft PR 程式就標為安全合規。
