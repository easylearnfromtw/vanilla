## Q01 / 50 — 設備適應與模型路由

**決策：D — 自動適應所有設備。已由使用者於 2026-10-20 確認。**

原始意圖：「手機、一般電腦、高效能電腦使用同一套 October 能力，但依硬體選用不同本地模型與授權節點。」

### 產品定義

- **統一入口與語意能力**：所有設備對外顯示 October（阿土伯），採相同任務 API、工具協定、任務狀態、成果報告格式及授權政策。
- **不以模型參數量定義使用者功能**：由 October 能力層管理知識檢索、確定性計算、任務分解、工具執行、排程與驗證；各設備選擇適合的推理模型。
- **硬體感知推理**：測量裝置類型、RAM／VRAM、電源、可用模型、推理健康度及回應延遲，在已授權的節點中進行健康檢查與選路。手機優先極輕量本機模型、一般電腦優先約 2B、高效能電腦優先約 4B 或適合的較大模型；這些是**目標等級，非已確認每部設備可執行的承諾**。
- **同功能入口不等於同等效能或同等離線品質**：不可用的節點或工具須明確顯示無法執行／等待授權，不能虛報完成。回退不得默默傳輸私人內容到未授權裝置或雲端。
- **本地優先、可替換核心模型**：October 不與單一 Qwen 權重綁定。Slime／Detroit 對接已授權設備與持久化 Agent Runtime；路由器不持有擅自擴權能力。
- **執行證據**：模型規劃、工具實際輸出、後端驗證與排程結果必須可分別稽核；相同工作 ID 有冪等保護。

### 驗收要求（未實作）

1. 同一份合成任務，在手機／8 GB Windows／16 GB Windows 或測試模擬器均接受相同的 October 任務結構。
2. 路由結果需附模型名稱、運行位置、授權來源與功能可用性，不得將配置檔宣稱為已微調的權重。
3. 指定設備離線、記憶體不足或節點故障時，能選擇已獲授權的備援，或回報阻擋原因，不得靜默上雲。
4. 分別檢驗品質（任務正確率、工具調用精度、數據核對）、成本、首字延遲、峰值 RAM／VRAM、電池消耗與任務完成率。
5. 保持嚴格租戶隔離、停止開關、工作佇列及高風險操作後端政策檢查。

## Q02 / 50 — 私人節點與雲端備援的自主授權路由

### 已確定決策

**Q02 / 50：C — 智慧混合運算。使用者於 2026-10-20 正式確認。**

使用者原始決策：「智慧混合運算，依預先授權的隱私、費用與供應商政策自主調度。」

#### 統一運算策略

1. **分層路由順序**：優先目前裝置的本地模型 → 經使用者／節點擁有人授權且健康的私人運算節點 → 事先允許的雲端模型／服務。順序可依工作性質、成本、負載與個別任務授權政策調整；每個候選都必須先通過權限與資料政策檢查。
2. **預先授權，而非每次打斷**：使用者或企業租戶先配置允許的提供者、裝置、資料類別、任務類型、預算上限、節點可用時段。僅在這些可驗證界線內自動調度；沒有授權時拒絕升級或要求額外授權。
3. **隱私分類**：私人模式、機密資訊、受規範資料預設不傳至其他裝置或雲端；除非該筆任務的有效授權政策明確允許其流向。外部檢索結果與提示文字不可修改資料流向政策。
4. **成本約束**：在送出可能計費的請求前，執行後端預算預留與租戶層上限檢查；累積用量和預算不得僅由 LLM 自述。未配置預算、計價資訊不可得、超過上限或政策不允許時，不得自動使用雲端。
5. **授權節點策略**：本人節點與經同意的朋友節點都須配對驗證、節點身分與健康檢查、撤銷權限、傳輸加密與資料隔離。朋友的設備不因加入叢集就取得其他使用者的任務資料或管理權限。
6. **結果與失敗處理**：保留路由決策理由、實際模型與節點、授權證據、成本估算／結算、已完成工具結果及錯誤原因。節點失聯或品質不足時，在原政策邊界內選擇備援，否則回報不可完成，禁止假裝成功。
7. **離線退化**：無網路時仍可使用裝置本身具備的模型與資料／工具；只有線上服務能做的任務不可宣稱已完成。不同等級設備具有一致任務介面，並不代表離線性能或品質完全相同。

#### 待填入的客戶級設定（尚未由使用者決定具體數值）

- 每月／每項任務預算額度與超額處理。
- 可用的雲端提供者、模型與資料分級清單。
- 私人節點的信任級別、硬體可用時段、運算成本分攤。
- 最高延遲容忍、降級門檻與路由品質目標。

#### Q02 驗收測試（尚未實作）

- 模擬本機資源不足時，核准的私人節點應可被選用；禁止的節點不得被嘗試。
- 私人與機密資料若未授權對外傳輸，模型不可為了提高回答品質而呼叫雲端。
- 超出預設預算或未設預算時，不得建立可計費請求。
- 節點下線與被撤銷後不得再接收任務；所有選路及阻擋原因可稽核。
- 維持 Q01 的統一 October 任務 API，不將路由視為擅自取得其他客戶的資料／工具授權。

## Q03 / 50 — 自適應混合專家架構（Adaptive Expert Orchestration）

**決策：D — 自適應混合專家架構。由使用者於 2026-10-20 確認。**

使用者原始決策：「輕量核心模型負責規劃，按需使用專業知識、計算工具、專科模型及已授權較大運算節點，不要求所有模型常駐記憶體。」

### 產品與技術定義

1. **October Core（常駐輕量大腦）**：在受限硬體上保留必要的任務理解、拆解、上下文摘要、工具選擇與結果檢查能力。核心模型可依 Q01 在不同硬體選擇不同參數大小，但介面與權限規則一致。核心模型不必靠權重記住五門專業的所有事實。
2. **Knowledge Experts（按需檢索）**：經濟、管理、財金、會計、精算與系統工程等領域使用獨立、可版本化、可更新的知識庫；RAG 返回來源、版本、適用日期、前提與可信度。保密資料須服從 Q02 的資料流向限制。檢索未命中不能編造專業結論。
3. **Deterministic Tools（確定性計算）**：指標、財報勾稽、NPV、損失模型、統計估計、單位換算與程式測試應盡可能由可驗證的程式計算，而非依靠模型臆算；每個工具有輸入／輸出 Schema、權限範圍、數值誤差容忍與成功證據。
4. **Specialist Models（選用專科模型）**：當核心模型的可靠度或任務複雜性不足，才載入可用的程式／數學／視覺／長文本等專科模型（不要求所有功能都靠不同專科模型）；同一時間只保留符合記憶體預算的活躍模型，必要時卸載與重載。
5. **Authorized Higher-Capacity Nodes（授權升級）**：複雜任務可按 Q02 的隱私、費用、供應商與節點許可移交至較大型模型；禁止將效能升級視為跨租戶、跨權限、跨資料分類授權。
6. **Detroit／Slime 為執行與運算層**：October 對外只提出結構化執行計畫；Detroit 的執行器做實際權限檢查、排程、工具呼叫、錯誤回復與稽核，Slime 負責健康、設備性能與推理節點選路。模型產生的文字或未信任檢索結果不能新增執行權限。
7. **按需資源調度**：以 RAM／VRAM、CPU／GPU 使用率、電池、模型冷啟動時間、KV cache、可用硬碟、網路延遲及成本決定是否預載、保持常駐、卸載或轉交任務，避免因多個專科模型同時常駐耗盡裝置記憶體。
8. **能力一致、品質可分級**：所有設備具有相同 October 功能入口；模型或知識源缺乏時需顯示降級、缺資料或無法完成，不能假稱有 60B 通用推理能力。針對指定專業任務，須以獨立 benchmark 實測準確性與工具完成率。
9. **專業分析需可審核**：財金、會計與精算模型的輸出須附幣別／單位、法規與會計準則版本、假設、敏感度、資料日期與適用邊界。高風險或不可逆行為由獨立政策引擎阻擋或核准。

> 術語界線：這裡的「混合專家」指系統層的 Agent + 知識庫 + 工具 + 多個可選模型的動態調度，**不是**已完成以 MoE 架構重新訓練一個神經網路權重模型。

### 驗收條件（尚未實作）

- 同一份跨經濟、管理、財金、會計與精算的合成案例，能按序調用知識檢索、確定性計算、結果驗證，提供可重現輸出與各階段證據。
- 在 RAM／VRAM 限制下限制同時常駐模型數量，觀察峰值記憶體、卸載耗時與失敗率。
- 注入專科模型缺失、網路中斷、節點故障、模型超時後，仍只能在 Q02 已授權條件內降級或升級，不得虛報成功。
- 針對高風險／專業任務，以盲測題、工具正確率、跨領域任務完成率、延遲和成本比較基礎小模型、October 混合架構與選定的大模型基準。
- 驗證無授權的跨租戶查詢、昂貴雲端推理、資料外送與任意高權限工具調用均遭阻擋。

## Q04 / 50 — 風險感知的動態推理（Risk-Adaptive Reasoning）

**決策：D — 風險感知的動態推理。由使用者於 2026-10-20 確認。**

使用者原始決策：「簡單任務快速完成，複雜與高風險任務自動增加推理、工具計算、交叉驗證及授權專科模型調度。」

### 核心政策

1. **逐任務分級，而非只看領域名稱**：由確定性政策引擎和輕量分類器共同評估任務複雜度、事實時效性、預期損失、是否涉及實際金錢／資料／系統寫入、隱私及可逆性。僅詢問財金定義不等於實際投資操作；實際操作則須提升風險層級。
2. **低風險／簡單任務（Fast Path）**：盡量用設備上的 October Core 直接回覆，縮短上下文和工具鏈；必要時核對基本事實。避免為每次閒聊啟動多個專家模型。
3. **中等風險／分析任務（Verified Path）**：分解問題，擷取領域知識並核對來源日期，使用可驗證的確定性工具計算，檢查結構化輸入／輸出與單位；在誤差超標或證據不足時回問、標記不確定或升級。
4. **高風險／專業決策（Deep Path）**：採多步規劃、敏感度與邊界測試、工具重算、必要時使用相互獨立的資料來源或授權專科模型進行交叉檢查；重要財務、會計、精算結果須揭露方法、假設、資料時間點、限制與風險。
5. **真實高權限／不可逆行為（Policy-Gated Execution）**：交易、付款、刪除、正式部署、修改帳務／存取權限等操作，不論模型信心如何，必須由 Detroit 後端執行器依授權、範圍、預算及必要核准處理。模型增加推理次數或取得其他模型同意，不能代替授權。
6. **動態推理預算**：依任務分級設定 token／步數／工具呼叫數／重試／耗時／RAM-VRAM／雲端費用上限。具體預設數值須在後續設定題確認並經實機測試，不在 Q04 憑空承諾固定秒數或正確率。
7. **成本與隱私優先序**：任何升級都先遵守已確認的 Q01 全設備適應、Q02 預授權混合運算與 Q03 按需專家架構；不得因風險高而突破外送禁令、租戶隔離或費用上限。高風險工作若無足夠合規資源，改回傳阻擋或待人工覆核。
8. **品質驗證與拒答機制**：分別記錄推理前風險分類、選擇的深度、實際工具結果、來源可靠性、最終成果與耗用資源；數值與工具結果若不一致，明確回報未驗證，不捏造完成狀態。
9. **LUCA 閉環改善**：收集經允許的非機密任務品質指標，分析錯誤類型與錯誤升級；回饋先改善路由與工具策略。只有經審核的資料集與保留測試通過後，才可另行微調 October 權重，並避免訓練／測試資料洩漏。

### 建議的風險級別（待校準，屬規格而非已上線）

| 級別 | 示範任務 | 運算與驗證方式 |
| --- | --- | --- |
| R0 快速 | 一般聊天、基礎解釋 | 本地核心優先，簡短回答 |
| R1 標準 | 文章摘要、公開數據整理 | 核對來源與基本一致性 |
| R2 專業 | 財報分析、NPV、精算情境、複雜程式排錯 | 檢索、程式計算、情境與結果驗證 |
| R3 高影響 | 真實帳務更改、交易、刪除、正式部署、授權修改 | 專業驗證 + 後端權限檢查與必要核准，禁止模型獨斷 |

> 嚴重度與推理深度不是一對一固定映射：風險低但難度高的純研究問題仍可用 Deep Path；風險高但很簡單的行動仍需政策閘門，不必浪費推理 tokens。

### 驗收測試（尚未實作）

- 同一設備上比較 R0／R1／R2：測量首字延遲、總耗時、工具呼叫數、能源／RAM／VRAM（若可取得）及盲測正確率。
- 注入錯誤來源、數值偏差與工具衝突時，R2 應進行重算或明確揭露未驗證，而不是以高信心給錯誤結論。
- 不得用「高風險」當作自動將資料送往未授權雲端的理由；超出預算、權限不足及租戶不符時應停止或降級。
- 針對 R3 進行無授權、提示注入、重試與不可逆操作案例，禁止未通過後端政策即執行。
- 比較同類任務在 Fast／Verified／Deep 三種運算路徑的品質提升與額外資源消耗，持續校準升級門檻。

## Q05 / 50 — 自適應資源管理（Adaptive Resource Management）

**決策：D — 自適應資源管理。使用者於 2026-10-20 正式確認。**

使用者原始決策：「採自適應資源管理，主動監測硬體負載、記憶體、溫度、電池及裝置閒置狀態，動態載入卸載模型、調整任務與排程，並在授權範圍內使用其他節點。」

### 執行與產品規格

1. **本地硬體感知**：October／Slime 依作業系統及使用者授權能力收集 RAM、VRAM、CPU/GPU 負載、溫度／散熱、電池／充電狀態、裝置閒置狀態、可用儲存空間、推論延遲與節點健康度。只能使用系統實際提供的訊號；缺失時標記 unavailable，不假裝已偵測。不得以資源診斷為由讀取非必要私人資料。
2. **前景工作優先與資源上限**：使用者正在工作、遊戲或視訊時降低 October 背景併發、CPU/GPU 份額與 I/O；明確保留系統 RAM／VRAM 餘裕，避免與桌面前景程式競爭。節點擁有者的資源、時間與暫停設定高於叢集效率。
3. **動態模型生命週期**：October Core 及專科模型採按需載入、可調整的短期 keep-alive、空閒卸載、熱模型緩存與冷啟動成本估算。不得強制在低規格設備同時駐留所有專科模型；工作切換與釋放資源須可觀測。
4. **能源／熱管理**：依電池電量、是否充電、過熱與散熱能力降低批次、併發及背景排程；必要時安全暫停／停止任務。溫度門檻以裝置規格、OS 指標及實際測試決定，不預設所有裝置都能讀到準確溫度。
5. **分層工作執行**：裝置可用時先執行合適的本地任務；不符資源或能耗限制時，改為耐久佇列、分塊處理、降載，或依 Q02 授權政策選取其他本人／友人節點或允許的雲端。禁止未經授權的任務外傳與額外付費。
6. **排程與恢復**：需有持久化 scheduler、工作狀態、逾時與重試限制、冪等鍵和檢查點。模型卸載、裝置休眠或重開時不能直接宣稱任務已完成；復原後應依證據重試或回報停止。

### 可靠性架構與執行契約

1. **以證據而非流暢度為標準**：October 需要區分「經驗知識／模型推論」「來源可追溯的資料」「工具計算結果」「外部執行回傳」「已獨立驗證」五種狀態；沒有足夠依據時說明不確定性、資料缺口與適用範圍，不把模型自信度當作真實機率或授權依據。
2. **Knowledge Grounding**：需要時效性或專門依據的任務，先從具來源、發表日期、有效日期及版本的專業知識庫／授權來源取得可查驗內容；每項重要事實要能追到對應證據。檢索不到、來源互相矛盾、引用與結論不符時，先標記未驗證，必要時補查而非自行捏造 DOI、網址、會計準則或研究結果。
3. **算術及專業數值檢查**：經濟、管理、財金、會計、精算的重要數字由確定性計算器重新計算，檢查公式、貨幣、時點、單位、輸入完整性、四捨五入容忍及假設。可加入情境分析、邊界條件與回歸測試。模型文字答案不能充當計算工具輸出。
4. **Verifier 與 Planner／Executor 分離**：October Core 可以建議計畫、回答與工具選擇，但 Verifier 必須獨立檢查結構化 schema、資料版本、數值、工具副作用證據及成功準則；另一個 LLM 的一致回答只能作輔助訊號，不能單獨視為事實或已執行證據。
5. **Detroit 執行證據鏈**：每次真實工具呼叫必須由可信後端產生 job_id、step_id、tool_id、verified_actor/tenant、授權決策、執行時間、狀態、外部回傳／版本、稽核紀錄與可驗證的結果參照。對外操作只有在取得相關服務確認及必要的事後讀取驗證後，才能標示 executed 或 verified。
6. **禁止虛報進度**：明確區分 planned、queued、running、executed_unverified、verified、failed、blocked、awaiting_approval、paused；未發送、未部署、未寫入、未調用工具、未下載或未測試時不得使用「已完成」之類字眼。對可觀測的外部副作用採服務端結果而非模型自述。
7. **風險感知驗證強度**：遵循 Q04 的 R0–R3 分級。低風險聊天不必額外呼叫多個模型，重要事實、法律／財務／會計／精算決策及實際外部操作增加來源、數值、狀態和授權檢查；嚴重不足時回問 Merlin 或停止。
8. **專門抗幻覺訓練**：設計包含缺乏證據、來源衝突、查無網頁、工具超時、偽造工具回覆、惡意提示注入、日期錯置、單位錯誤、跨租戶要求、未經授權操作等正反訓練案例；只用已授權、經審核且去重的資料進行 SFT／偏好訓練，分離真正未見過的測試題。增量調整不代表自動更新 Qwen 權重。
9. **失敗處理與明確停損**：遭遇計算不一致、來源缺失、工具失敗或驗證不通過時，在 Q02 授權與成本、Q05 資源及 Q07 安全重試上限內重算、補查或局部重規劃；超出限制則回傳錯誤與原因，不能假裝成功或繞過安全政策。
10. **LUCA 可追溯品質指標**：在隱私同意與最小化資料原則下統計事實支持率、引用對應正確率、專業數值正確率、虛構工具調用率、虛假完成宣稱率、已執行但未驗證比例、拒答／回問精確性、延遲與成本；用獨立盲測與實際失敗分析監督品質改進。
11. **輕量模型優化**：將檢索、計算、來源和執行證據儲存在可追溯的外部結構化紀錄，核心模型按需讀取摘要；避免將全部資料堆進小模型上下文。只在需要時以 Q03 的專業工具、專科模型或已授權大節點提升品質。

### 驗收測試（尚未實作）

- 以已知有答案與明確無答案的混合題，測量錯誤斷言率、正確拒答率及有來源主張的實際證據支援比例。
- 在偽造 DOI／網址、過期 IFRS／精算準則、財務單位錯置、錯誤時區或互相矛盾來源的案例中，October 必須指出或追查問題，不得給出虛假的精確答案。
- 模擬工具沒有被調用、只收到 HTTP 202、工作逾時、交易失敗與回滾不可能情境，對外狀態不能在缺少可信證據時標記 verified/completed。
- 在多租戶與提示注入情境下，外部文件／工具輸出不得修改後端權限、隱私政策或證據驗收標準。
- 對跨學科財務計算進行程式化參考答案核對，數值錯誤、公式錯誤與假設缺失不得通過獨立 Verifier。
- 與僅做 Prompt 防幻覺提示、全部任務強制檢索、單純模型信心門檻三種基準比較任務品質、延遲、成本及資源消耗。不得宣稱能保證零幻覺或全面達到 60B 通用推理水準。

## Q10 / 50 — 多層次自主學習、審核式微調與安全版本升級（Layered Continual Learning）

**決策：D — 多層次自主學習系統。由使用者於 2026-10-20 明確確認。**

使用者原始決策：「日常以知識檢索、記憶、LUCA回饋及工具策略改善；經使用者同意且審核的資料再交由獨立訓練節點批次微調權重，經盲測、回歸測試與版本核准後才更新，失敗則保留舊版。」

### 產品架構與訓練契約

1. **三層改善機制明確區分**：第一層 Runtime Adaptation（當次任務的查證、重規劃、知識檢索與結果驗證）；第二層 Strategy Adaptation（在合法且最小化回饋基礎上調整工具選擇、風險門檻與工作流程）；第三層 Weight Adaptation（授權且經審核資料的真實 SFT／LoRA／QLoRA 等權重更新）。不得把第一、二層改善誇稱為基礎語言模型已重新訓練。
2. **一般使用者端盡量零訓練負擔**：手機、PWA 及低階設備主要執行輕量推論與許可範圍內的檢索，不默默在背景使用用戶 GPU 做模型微調。真正耗資源的訓練由擁有者明確授權的獨立訓練節點承擔，並受 Q02／Q05 的運算成本、設備使用時段與能源限制。
3. **資料取得的明確同意與範圍**：使用者對話、個人記憶、客戶商業機密、醫療／財金資訊及跨租戶資料，預設不自動加入共享訓練語料；必須具備可驗證的同意、資料使用權、目的、保留期限、刪除及撤銷機制。私人模式不得用於模型訓練；跨租戶訓練不得因共享 October 平台而默認。
4. **回饋分離與品質控制**：LUCA 可在授權範圍內收集最小化錯誤類別、可驗證成功／失敗指標、所用模型和工具版本；NOODLES 對使用者主動選擇的答案和授權案例進行策展。偏好訊號不等於事實正確；高風險數學、財金與精算案例需計算器、專業資料或專家審核作為標籤依據。
5. **版本化資料集與防污染**：每一筆可訓練案例附來源、授權、時間、專業領域、資料版本、難度、可信度與去識別化狀態。移除重複案例、矛盾標籤、秘密和提示注入；保留真正未用於任何訓練／調參的獨立盲測題、跨設備任務測試與舊能力回歸集，防止訓練／評估洩漏。
6. **專業知識更新優先於不必要微調**：時效性法規、會計準則、經濟數據和研究文獻優先更新可追溯、帶有效日期的 RAG 資料與確定性工具，而非將變動中的知識反覆寫死在小模型權重；權重訓練主要改善任務理解、工具選擇、嚴謹推理結構、抗幻覺和格式遵循。
7. **受控的批次訓練管線**：由獨立節點執行明確配置的資料校驗 → 基礎權重與授權檢查 → LoRA／QLoRA 訓練 → 訓練日誌與輸出雜湊紀錄 → 盲測／回歸測試；支援固定種子、可重現版本、失敗中止與訓練產物隔離。未發生真正梯度更新不得宣稱「已微調」。
8. **晉升與退版政策**：新 adapter／模型先作離線盲測及 shadow evaluation，再依平台授權進行小比例 canary 和品質監控；須同時符合專業正確率、工具選擇、安全阻擋、隱私隔離、延遲、RAM／VRAM 與成本門檻。通過獨立審核和版本核准後才能升級；任何指標惡化則停止晉升、還原上一個已驗證模型與策略版本。不得因總平均分提高就忽略高風險回歸。
9. **模型路由與權重版本獨立**：October 是統一能力品牌，可依 Q01／Q03 選用不同大小和專科模型。每個節點回報實際 checkpoint、量化格式、adapter 及工具策略版本；改變 Ollama Modelfile 或 Prompt 不是權重訓練，需清楚標示。
10. **回饋閉環可稽核**：將錯誤事件轉成候選修復（工具規則／RAG／資料策展／微調需求），記錄所需證據、審核者、實際訓練 run、盲測差異與發布決策；小模型主動提出改進可以，但不得自行取用私人資料、突破執行權限、靜默替換正式模型或自稱達到 60B 通用能力。
11. **現況邊界**：既有 October Policy Head 合成決策分類的權重訓練，不等同 Qwen 基礎語言模型的財金／精算知識微調；本決策確定未來開發方向，**不代表**完整版自主收集、LoRA 訓練或正式版本熱替換已實作。

### 可量化驗收要求（未宣稱已完成）

- 在手機／一般 Windows／運算節點環境比較啟用學習回饋前後的常駐負載、推論延遲、GPU 使用與電池消耗；一般使用者端不得因權重訓練遭未授權的背景資源占用。
- 模擬私人模式、撤銷授權、含金鑰或私人財務資料、不同租戶與受限制模型輸出等案例，驗證不進入不適當的共享資料集。
- 以專家驗證的計算題、工具操作題、無答案／來源衝突題、舊版回歸題和新領域盲測題評估；防止只改善特定合成資料分類的單項分數。
- 留存每個正式發布版本的基礎模型、adapter、資料集雜湊、評估報告、執行權限政策、審核紀錄和回退途徑。
- 故意製造新模型幻覺率提高、跨租戶工具誤選、財金計算退步與推論超 RAM 上限的案例，驗證發布閘門會拒絕升級或回退。
- 對單純 RAG 更新、策略路由更新與真正權重微調三類改善提供不同驗證欄位，禁止用 Prompt 變更偽裝權重學習。

## Q11 / 50 — 固定工作流程模板、自動選用與受控工具執行（Template-First Orchestration）

**決策：C — 固定工作流程模板。由使用者於 2026-10-20 明確確認。**

使用者原始決策：「採固定工作流程模板，由 October 自動選用合適模板。」

### 設計定義

1. **模板優先，而非開放式全工具搜尋**：October 以事先定義、版本化且已驗證的工作流程為主要執行單位。October Core 解析使用者目的，選出最適用的模板，不要求使用者熟悉 Scout、CREAM、Orchestra 等工具名稱。不得假設 October 可在正式執行時任意拼接所有已安裝工具。
2. **模板契約**：每個 Workflow Template 明定 template_id、版本、適用意圖、必要／可選輸入、步驟依賴、允許的工具及版本、輸入／輸出 schema、費用／資源預算、租戶及資料權限、風險等級、驗證規則、重試上限、恢復／補償措施及成功標準。
3. **初始範本類型（僅為候選規格）**：公開市場研究 → 來源核對 → 財務分析 → CREAM 圖表 → Orchestra／DeckCraft 簡報；經授權的 LUCA 系統監測 → 唯讀診斷 → 分析報告；文件資料擷取 → 計算／會計勾稽 → 專業報告；授權的排程報表；其他模板須經建置、測試及核准後加入。
4. **模板選擇而非盲目執行**：在已安裝且獲授權的模板索引中，以意圖相似度、必備參數、裝置能力、資料分類、成本、使用者授權、工具健康度和風險評級篩選。當無足夠匹配時應安全降級至只讀分析、提出新模板草案或請 Merlin 詢問關鍵差異，不得捏造存在某個模板。
5. **模板內的受控動態性**：Q07 的動態規劃仍適用於模板內的條件分支、參數填入、執行順序修正、安全重試及檢查點；所有可執行分支須預先定義在模板的權限邊界內。October 不得自行產生新工具權限或跳過必要驗證。依 Q12 追加規則，事先授權的低風險模板可通過後端自動政策審核後發佈至限定範圍；高風險／具副作用模板仍需 Ceres 管理員核准。
6. **Detroit／Diana 分工**：October 辨識任務並提出模板選擇；Diana 可搜尋核准模板、比較候選、填入參數並判斷是否滿足前置條件；Detroit 以可信後端身份逐步執行模板限定的工具；Verifier 逐步核對成果；LUCA 記錄失敗與品質；Ceres 供已授權管理者核准新增或更新模板。
7. **性能與維護性**：核心模型只接觸少量候選模板摘要與當前步驟，不把所有工具詳細說明塞進上下文；模板索引和工具 schema 版本化，支援離線載入、按需工具啟動與 Slime 節點調度。避免模板過多導致小模型無法可靠選擇。
8. **跨模板工作**：當需求涵蓋多項能力，可在事先核准的複合模板下串接子模板，輸出相同格式的中間產物與驗證證據。沒有核准的跨模板組合不得直接建立任意具副作用的工作鏈。
9. **外掛安全**：模板能使用的外掛與工具，須由後端確認其實際存在、版本、執行環境、tenant scopes、費用及權限，並遵守 Q02 的資料／雲端政策。外部文件或模型回覆不得偷偷修改模板內容。
10. **與 Q03／Q06／Q07 的關係**：固定的是『核准工作流程的結構及可用分支』，不是固定所有模型能力。Q03 仍能按需提供專業模型與檢索，Q06 在授權事件下自動啟動已核准模板，Q07 在模板內進行有限動態規劃與獨立驗證。

> 本題確定的實作取向是 **C：模板優先**，不是前一題介面中推薦的 D「全工具動態註冊中心＋任意自主編排」。工具註冊資料可用作模板的合法性檢查，但不能被默認為具有自由擴充／組裝新工作流的權限。

### 驗收測試（尚未完成正式實作）

- 使用者只說「研究公司市場並製作財務簡報」，October 必須在已核准模板中選擇正確工作鏈、補齊允許的參數、交由 Detroit 執行，無須使用者手動點選工具。
- 對同一任務測試錯選模板率、參數填入完整性、必要驗證是否被保留，以及 CPU、RAM、token 和冷啟動負擔。
- 故意要求不存在的功能、未核准的工具或不能組合的模板時，應回報缺少能力或提出模板草案，不能謊稱已執行。
- 模擬工具逾時、輸入資料矛盾和專科模型不可用，須沿模板允許的分支做安全重試／恢復，遵守 Q02、Q04、Q05、Q07、Q09 的限制。
- 未經許可的跨租戶資料、外掛權限、昂貴雲端節點及對外寫入，即使在模板內也必須由 Detroit 強制阻擋。
- 範本升級／退版須留下模板 ID、版本、差異、測試證據及核准紀錄，不因模型高信心而自動切換未審核的生產工作鏈。

## Q12 / 50 — 分級自主擴充與安全模板發布（Tiered Autonomous Template Lifecycle）

**決策：D — 分級自主擴充。由使用者於 2026-10-20 正式確認。**

使用者原始決策：「October 自動建立與測試模板，預授權低風險模板可自行發布，高風險或具外部副作用的模板需 Ceres 管理員核准。」

### 模板生命週期與權限政策

1. **以 Q11 的模板優先架構為基礎**：既有核准模板是預設執行方式；當沒有合適的模板，October 可以辨認缺失能力、推導輸入輸出契約、規劃新模板及其依賴。但新模板在正式執行前必須先完成模板型別及風險分類。
2. **自主候選建置**：由 October 提出 template_id、版本、適用意圖、輸入／輸出 schema、僅能使用的已登錄工具／版本、條件分支、依賴 DAG、資料分類、成本與時限、必要驗證、失敗行為及權限最小集合；Diana 提供核准工具對應建議，不能直接新增未知權限或自行批准全新外掛。
3. **沙盤及靜態驗證先行**：Detroit 在隔離沙盤中以合成／去識別化樣本執行 schema、工具可用性、錯誤恢復、資料外洩、租戶隔離、權限範圍、預算、冪等與提示注入測試；避免沙盤測試直接接觸生產系統、真實付款或對外通訊。
4. **分級核准模型**：
   - **T0 無副作用且已預授權**：僅使用使用者事先授權的只讀／純計算／本地格式轉換工具；不讀取未授權敏感資料、不向外傳送、不安裝程式、不新增憑證、不改動持久系統狀態。通過自動化後端政策、完整測試與預先授權的模板發布範圍後，可由 October **自行發布模板至該使用者或租戶核准的限定目錄**，不必每次請 Ceres 人工核准。
   - **T1 需核准／受限副作用**：新增檔案、修改設定、對外發送、執行具網路外送或費用風險的服務等，候選可自動生成及沙盤測試，但正式發布、啟用與實際有副作用的執行須由可信後端依操作分類和 Ceres 管理員核准處理；不可將模板核准視作所有個別高影響行為已獲核准。
   - **T2 高影響／危險擴權**：權限調整、正式部署、程式套件安裝、支付／交易、不可逆刪除、跨租戶存取、存取敏感資料或新增執行程式碼等，預設阻擋自動發布。必須經安全審核、必要的額外環境限制、Ceres 管理員明確核准及相關後端政策檢查；不符合政策的候選直接拒絕。
   - 實際分類以後端較嚴格的規則為準；**低風險不代表任何只讀資料都能任意存取**，資料讀取本身仍需原始授權與隔離。
5. **模板自動發布的意義及界線**：僅代表新增已驗證的**宣告式模板紀錄**到允許的模板目錄，不代表任意安裝第三方程式、執行 shell、正式部署網站、將資料或模板公開給所有用戶，亦不解除模板執行時的逐步授權。
6. **自動發布閘門**：正式目錄上架前必須滿足核准模板類型、工具與版本白名單、風險上限、權限不可升級、有效授權、通過沙盤驗證、明確驗證報告、費用上限與資源約束等條件。任何條件未知、驗證失敗、風險分級不一致或可疑提示注入，都應降級成 pending_review／blocked，不得由模型自我宣稱「已通過」。
7. **Ceres 管理者工作流**：需要核准時，Ceres 只發送最小必要的待審摘要及政策差異，管理員可查看受影響工具、資料／費用／執行權限、驗證結果，並選擇批准、拒絕或要求修改。權限與核准結果由可信後端保存，Telegram 文字指令不得繞過身分驗證及授權。
8. **版本化、測試與可撤回**：每個模板都應有版本、結構雜湊、來源、風險等級、發布者身分、政策版本、測試證據和審核紀錄；先在限定範圍 canary，再視評測結果升級。可停用、回退至舊模板版本並撤銷部署資格；已發生的外部副作用不能宣稱能完全回滾。
9. **動態執行不等於任意工具調用**：正式任務仍由 October 選取核准模板、Detroit 驗證各步驟的當下權限、Verifier 確認結果並由 LUCA 記錄。Q07 局部重規劃僅能在模板允許的結構／分支中運作；若需新增權限或具副作用流程，應先建立下一版候選重新走審核。
10. **遵守先前決策**：本機／私人節點／雲端選路受 Q01、Q02、Q05 約束；專家工具按 Q03 動態載入；Q04、Q06 的風險及主動性不會授予額外權限；Q09 的實際執行證據不得用 LLM 描述代替；Q10 的訓練改善與模板更新分別版本化。

### 驗收測試（尚未實作）

- 給定不存在但可由既有核准只讀工具完成的新工作，October 產生 T0 模板，通過沙盤與政策檢查後自動發布到該租戶的授權目錄；不應要求逐步人工核准。
- 模擬使用者要求跨租戶財報、私人資料外傳、權限提升或外部付款：不得偽裝為 T0；自動發布必須遭拒絕，需依類別轉送 Ceres 審核或直接阻擋。
- 測試失敗的 schema、工具不存在、非白名單工具、成本無上限、模板包含提示注入、狀態回傳造假及沙盤測試未完成時，應禁止發布。
- 對 T1／T2 模板，未收到有效管理員核准前，不能在正式環境發布或執行有副作用的步驟；核准不應跨範圍或永久有效。
- 模擬模板發布後工具版本更新、政策撤銷、節點故障或安全缺陷，系統應自動停用受影響版本並保留可稽核的回退記錄。
- 衡量新模板匹配正確率、自動沙盤通過率、錯誤風險分類率、未授權發布率、驗證錯誤率、每個模板創建成本和低配置設備記憶體負擔。

> **與 Q11 的銜接**：Q11 選 C，規定 October 執行工作時以核准固定模板為入口；Q12 選 D，規定遇到缺少模板時允許「自主建立、測試、分級發布新模板」。兩者相容。Q12 的自動發布僅適用在預先授權的低風險模板及其限定目錄，高風險與具副作用者仍須由 Ceres 管理員核准。

## Q13 / 50 — 分級自主第三方外掛整合（Tiered Autonomous Plugin Integration）

**決策：D — 分級自主外掛整合。由使用者於 2026-10-20 正式確認。**

使用者原始決策：「October 自動研究、產生Adapter、測試與評估風險；已核准來源、低風險且預授權的宣告式整合可自動啟用；新可執行程式碼、敏感資料存取與高權限外掛必須經安全審查及Ceres管理員核准。」

### 擴充架構與限制

1. **研究與盤點**：October 可在獲授權的存取範圍內解析 GitHub 開源專案或第三方工具的實際版本／commit、官方文件、API 介面、依賴、維護狀況、許可證與預定商業使用相容性；找不到依據須標記未驗證，不臆測程式碼內容或安全性。
2. **Adapter 產生與版本固定**：針對合適工具提出 Detroit Adapter 候選，描述 adapter_id、來源 repo／URL、固定 commit／release、版本相容性、輸入／輸出 schema、呼叫範圍、授權身分、網路出口與副作用、成本／速率限制、預期證據及超時重試行為。產生的 Adapter 不代表已安裝或已取得憑證。
3. **宣告式與可執行程式碼分離**：低風險自動啟用僅限於**已核准的來源、版本及 Adapter 類型**，使用預先提供的可信執行器、有限白名單 API／唯讀能力、不含新的可執行程式碼／任意 shell、未增加資料外送、憑證或權限，且由後端確認預授權仍有效。新增第三方程式碼、依賴安裝、容器映像、插件腳本、動態程式載入均不屬此自動啟用例外。
4. **安全供應鏈檢查**：候選需經許可證與再散布檢視、相依套件檢測、弱點掃描、惡意行為及網路外送評估、機密掃描、版本鎖定及風險評級。可產生 SBOM、來源追溯與雜湊；沒有發現弱點不等於保證安全，掃描失敗或結果不完整不得當作通過。
5. **隔離沙盤**：以合成或明確授權測試資料在限制 CPU／RAM、網路出口、檔案系統、執行時長及最小權限的測試環境驗證 Adapter。沙盤不得直接取得正式環境密鑰、管理員權限、跨租戶資料或真實付費能力；不可信外部 README／網頁內容不得當成更高優先級指令。
6. **分級發布規則**：
   - **P0 低風險宣告式整合**：若來源／版本／可信執行器／工具權限／資料流向均已在後端預先白名單，符合 Q12 低風險模板邊界且通過測試，可由 October 自動登錄並在限定租戶目錄中啟用；啟用也不能擴充任務 scope。
   - **P1 新整合或受限副作用**：建立新的 Adapter 程式碼、讀取額外資料、對外傳送、取得 API 憑證、改變網路出口或安裝執行依賴時，必須提交安全審查與 Ceres 管理員批准後才能部署或啟用。
   - **P2 高權限／高影響外掛**：需要系統管理、程式任意執行、正式部署／刪改資料、跨租戶資訊、付款／交易或其他敏感操作時，預設禁止自動部署，需經更嚴格的後端政策、技術審核與明確管理員核准；核准未滿足則阻擋。
7. **憑證與權限絕不自動提升**：API key、OAuth token 和憑證應透過受控祕密管理及後端授權機制配置；October 不能從對話讀取、回顯或移送其他使用者的密鑰，也不能自行提升 permission scopes。Ceres 只執行已驗證擁有者身分的核准流程，核准必須限時、限範圍且可撤銷。
8. **模板整合一致性**：Q11 的正式使用入口仍是核准工作流程模板；Q12 能分級自主擴充模板，但新外掛須先依本題 P0–P2 完成整合審核，再被後續模板引用。自動產生 Adapter 不能繞過 Q11／Q12 的工作流程發布政策；實際執行逐步驗證權限。
9. **持續性監控與中止**：LUCA 記錄插件實際版本、錯誤率、延遲、資源／費用、異常呼叫與授權拒絕；發現依賴弱點、版本漂移或執行異常時可在後端停用，必要時回退 Adapter 與模板到最後一個核准版本。已外送的資料或不可逆行為不能聲稱可完全回滾。
10. **開放原始碼授權界線**：自動整合必須評估是否允許修改、商用、發佈、連結與衍生作品；適當保留歸屬、授權與告知義務。若不確定是否與 Vanilla 的預定商業用途相容，標記待法律或專業人工確認，不能由模型自行推定合法。
11. **未實作與已實作分開**：Q13 僅確立技術規格，不能據此宣稱 October 已自動閱讀任意 GitHub repo、已下載程式、完成掃描、部署 Adapter 或正式授權外掛。所有執行成功與核准狀態需依 Q09 可驗證實際紀錄。

### 驗收測試（尚未完成正式實作）

- 在已核准來源／版本／唯讀 Adapter schema 與有效預授權下，應可通過 P0 沙盤測試並自動啟用；每步可查到實際的來源、測試與授權證據。
- 同一來源若提交新的可執行程式碼、更新依賴或新增 API scope，應從 P0 升級為至少 P1，未經管理員核准不得安裝或執行。
- 模擬 README 惡意提示注入、假冒安全掃描、未固定版本、感染相依套件、對外資料外送與竊取密鑰，必須阻止自動啟用並保留診斷。
- 對含有不相容授權、跨租戶資料、計費 API、系統管理與高影響操作的外掛，應阻擋未經核准使用，且不能誤分類為 P0。
- Ceres 管理員拒絕、權限撤銷或插件遭停用後，Detroit 不得繼續執行其 Adapter 或調用原有令牌。
- 比較固定模板配備核准 Adapter 與小模型自由選擇所有工具：衡量正確工具調用率、未授權執行率、平均延遲、記憶體、失敗率及人工核准負擔。

## Q14 / 50 — 統一資料契約＋成果交換系統（Typed Contracts & Artifact Exchange）

**決策：D — 統一資料契約加成果交換系統。使用者於 2026-10-20 正式確認。**

使用者原始決策：「小型結構化資料使用 JSON Schema，大檔案以 Artifact Store 參照傳遞，包含來源追溯、版本管理、權限驗證與 Detroit 工作檢查點。」

### 架構與資料交換契約

1. **Typed Data Contract**：Scout、CREAM、Orchestra、WordCraft 及其他受核准的 Detroit 工具，必須公開明確版本的輸入／輸出 JSON Schema；資料欄位包含語意型別、必要性、單位、貨幣、時區、統計口徑、來源引用與錯誤型別。由可信後端在執行前後驗證；LLM 不能自行宣稱 schema 合格。
2. **小型結構化訊息**：以受限大小的 JSON 傳遞數值、文字摘要、引用、結構化圖表資料、步驟狀態與 artifacts 參照；使用標準 Envelope（contract_version、job_id、step_id、producer、tenant_id、schema_id、data_classification、timestamp、payload、artifact_refs、status、evidence_refs）。大型原始資料不得無限制灌入小模型上下文。
3. **Artifact Store**：文件、簡報、試算表、圖片、影像、大型資料表、原始抓取內容等以受保護物件儲存方式管理，由 artifact_id／內容雜湊／mime_type／size／version／tenant／classification 等 metadata 參照，而不是在 JSON 內嵌整份二進位內容。對來源讀取與下游工具交接提供時間受限、scope 受限的存取方法。
4. **Provenance 與可驗證性**：每份成果記錄原始來源與取得時間、處理工具／版本、輸入 artifact refs、計算參數、輸出 hash、job／step 身分、驗證狀態。統計與財務輸出應保留必要的原始單位、轉換方法及計算假設；下游不得將無法核對的文字摘要當作唯一數據依據。
5. **版本與 schema 相容性**：schema、工具與 artifacts 各自版本化。不同工具契約不相容時，先透過經測試、已授權的轉換 Adapter 執行顯式 migration，通過資料完整性檢查才可續行；不能依賴小模型臨時猜欄位或默默丟棄重要資料。
6. **Detroit 流程與 checkpoint**：所有交換由 Q11 核准模板與 Q12 受控擴充工作流管理。持久化記錄 job_id、step_id、input_ref、output_ref、contract_version、artifact_hash、verified_status、checkpoint、attempt_count、idempotency_key；重新啟動只重做尚未確認完成且可安全重試的步驟。
7. **授權、租戶與資料所在地**：每次工具讀取、轉換、寫入與節點傳輸皆由後端核對租戶、身份、用途、資料分類、來源、預算及 Q02 運算／雲端授權。共用 Artifact Store 的基礎設施不表示跨租戶共享內容；私人模式與敏感內容遵守其獨立保留／外送政策。
8. **交易性寫入與生命週期**：artifact 先寫入暫存區、驗證完整性及 hash 後才標記可供下游使用。設置防篡改、加密、保留期限、存取撤銷、刪除及垃圾回收政策；引用失效、驗證不通過、資料損壞或權限遭撤銷後不得繼續當作有效成果。
9. **工具錯誤契約**：統一區分 schema_invalid、missing_artifact、permission_denied、source_unverified、tool_timeout、transient_failure、unsupported_format、budget_exceeded 等錯誤，讓 Q07 Planner 能在模板核准的路徑內安全重試、降級或依 Q08 回問，而非虛構工具已成功。
10. **輕量模型與跨設備支援**：October Core 只接收當前步驟所需摘要、schema 核心欄位和可取回的 artifacts handles；高負載轉換工作交給 Q01／Q05 規範的適當節點。跨節點分配要受 Q02 授權、資料本地性及成本限制。
11. **真實執行證據**：工具返回內容、文件實際存在、產物完整性、版本與 schema 驗證結果，必須由 Detroit Executor／Verifier 確認。未實際完成轉換、未核對來源或 Artifact Store 寫入失敗，不可報告為已生成成功。
12. **狀態界線**：本題是 50 題架構決策，並不表示正式環境已經部署 Artifact Store、跨工具 schema 轉換器或分散式 checkpoint。上述項目仍需程式實作與端對端驗收。

### 驗收測試（尚未完成正式實作）

- 在 Scout 網頁來源 → CREAM 財金計算 → Orchestra／WordCraft 文件成果 → Verifier 的合成鏈中，驗證每一步標準資料契約、單位、來源、版本、artifact refs 及結果可追溯。
- 傳入缺少必要欄位、數值改成字串、時區／貨幣錯誤、schema version 不相容、mime_type 不符或檔案內容與 hash 不一致時，應被明確阻擋，不可默默接受。
- 大型 PDF、試算表及圖片必須以 Artifact Store 參照交接；在小型本地模型環境測量記憶體峰值與上下文 token 消耗，確認沒有將整個檔案塞入 Prompt。
- 模擬不同租戶、私人檔案、過期 artifact 權限、撤銷同意、未經授權雲端節點和跨裝置存取：不得洩漏資料，並在後端留下權限拒絕證據。

## Q15 / 50 — 自適應分散式調度（DAG-Aware Adaptive Distributed Scheduling）

**決策：D — 自適應分散式調度。由使用者於 2026-10-20 正式確認。**

使用者原始決策：「結合 DAG、硬體資源監測、任務優先級、Slime 已授權節點調度及 Detroit 持久化執行與驗證，自動控制平行數量、等待、轉移、恢復與成本。」

### 調度架構與執行契約

1. **有向無環依賴圖（DAG）**：October 於 Q11 已核准模板、Q12 經核准擴充模板的界線內產生具有 task_id、step_id、dependencies、inputs、outputs、expected_evidence、risk_class、estimated_resources 的結構化工作圖。無上游依賴的只讀工作可平行執行；需要數據、artifact 或授權確認的下游工作必須等待前置步驟驗證通過。
2. **Detroit 為可信執行／排程控制面**：由具持久化狀態的 scheduler 管理排隊、租戶配額、優先級、租約（lease）、心跳、超時、取消及重試；October 的模型推論只是計畫建議，不能直接宣告工作已成功。調度狀態與 Q07 checkpoint、Q09 執行證據、Q14 Artifact Store 對應。
3. **Slime 節點容量評估**：在節點擁有者允許的監測能力內收集 OS、CPU/GPU、RAM/VRAM 餘裕、電源／溫度、已安裝模型與工具、網路可達性、資料本地性、延遲、排隊時間及健康度。訊號不存在時明確標記 unknown，不能推測該裝置必定可執行某模型。空閒與高負載策略遵守 Q05。
4. **授權優先的節點篩選**：任何節點在成為候選前，須通過 Q02／Q13 的租戶、資料分類、外送、節點擁有者同意、工具 scopes、雲端供應商及費用上限檢查；不可為了提高吞吐量把資料移到未授權的朋友電腦或雲端。
5. **成本與效益感知的選路**：在合格節點中平衡預估總完成時間、傳輸成本、排隊延遲、模型冷啟動、記憶體與電池耗損、雲端費率、任務優先級和驗證需求。使用可觀測的用量與預算預留；資訊不足時選較安全的節點或排隊，不擅自計費。
6. **受控平行與背壓**：每台設備依可用資源與擁有者上限設定最大並行工作、GPU/CPU 資源預留、傳輸速率與 Artifact I/O 限速；不足時降低並行數、排隊、暫停低優先任務或選合規備援。不可因多個低規格節點同時在線就假定它們能無成本合併單一大型模型的 VRAM。
7. **任務優先級及公平性**：以已授權的緊急程度、期限、風險、工作互動性、租戶配額與老化（aging）避免飢餓；前景使用者任務優先保護，低優先背景工作不得長期占用朋友設備。排程參數與預算需可配置並可審核。
8. **工作分配與依賴證據**：每個完成步驟返回符合 Q14 schema 的結果與 artifact refs，經 Verifier 驗證才解鎖依賴步驟。對財務、會計、精算計算須保留公式、來源、單位與必要數值證據。資料流動不可只靠 October 將自然語言摘要複製給下一個工具。
9. **失聯、故障與安全重試**：租約過期、節點下線、工具逾時或結果驗證失敗時，將工作標記為 uncertain/failed 並先查既有執行證據；只對已證明具冪等性、未發生不可逆副作用的步驟安全重試或重新派送。涉及發信、付款、部署和刪除等操作，禁止因節點失聯而盲目再次執行。
10. **持久化與恢復**：保留 job_id、DAG revision、step state、lease owner、heartbeat、retry count、checkpoint、artifact hash、verification status、已花費成本及政策版本。伺服器重啟或手機關閉後，只有在合法且常駐的 Detroit 節點上才能繼續背景任務；不可宣稱瀏覽器本身擁有可靠常駐執行能力。
11. **安全停止與作業回報**：Ceres 授權管理者或作業擁有者可取消、暫停並撤銷後續派工，立即阻止新的執行步驟；已完成的副作用仍須清楚揭露且只按核准流程補償。LUCA 記錄每步節點選擇理由、資源使用、費率、排隊延遲、工具呼叫及驗證狀態。
12. **分散式任務與模型平行化分界**：本題確認的是**工作與工具任務層級的跨節點調度**；並未決定或實作 tensor/pipeline parallel、KV cache 分片、遠距 GPU 記憶體共享等單一大型模型分散式推論。若未來要跨低階設備跑大型模型，需要另行評估網路頻寬、延遲、硬體／後端支援與準確性。
13. **與 Q01–Q14 一致**：前端保有單一 October 能力入口；規劃、風險分級、模型與專家選擇、模板、Adapter、來源資料、隱私與認證均以已確認政策及後端事實為準。多節點可用不等於允許權限擴張。

## Q16 / 50 — C＋D：量化經濟預測 × 多學派實證驗證（Quantitative Economics & Evidence-Based Pluralism）

**複合決策：C＋D — 經濟模型與量化預測優先，同時採多學派、實證數據與模型驗證。由使用者於 2026-10-20 正式選擇。**

使用者原始答覆：「C+D」。本題明確允許兩方案**同時成立**，不改寫成單選 D。

### 綜合定位

October 的經濟學專業能力以 **C：結構化計量模型、量化預測、反事實與情境模擬** 作為主要分析方法，並以 **D：主要經濟學派的傳導機制、可追溯數據來源、不同假設與獨立驗證** 作為理論與實證基礎。面向台灣、美國、中國及全球經濟的交互影響，清楚區分解釋、因果推斷、預測與決策建議。

### 模型與知識設計契約

1. **理論基礎與學派差異**：覆蓋個體與總體、古典／新古典、凱因斯及新凱因斯、貨幣學派、金融不穩定／信用週期、新成長、新結構經濟學及制度經濟觀點；記錄每個模型的前提、傳導機制、適用條件與可能反例。不得把相互衝突的學派主張混成假共識。
2. **專業知識庫及文獻**：參考 Mankiw、Blanchard、Keynes、Friedman／Schwartz、Minsky、Kindleberger、Romer、Krugman 等理論脈絡；東亞／中國經濟涵蓋林毅夫、蘭小歡等研究與不同政策框架。優先以合法取得、版本化的原創摘要與引文索引存放，不擅自複製受版權保護的完整著作。
3. **可追溯數據層**：使用統計機關、中央銀行、國際機構及其他已授權可靠數據源的 GDP、CPI/PCE、薪資、就業、利率、貨幣／信用、債務、匯率、進出口與金融條件資料；每筆保留地域、單位、頻率、統計口徑、季節調整、發布日期、修訂版本／data vintage。無即時來源不得假稱取得最新數據。
4. **C：量化方法能力**：根據資料量與問題使用可驗證的 IS–LM、AD–AS、Solow、國際收支／開放經濟框架、VAR／SVAR、ARDL、迴歸、時序預測、成長會計、壓力測試及其他適當方法；DSGE、因果識別或其他重型模型只在具有合適參數、辨識條件與計算資源時使用。模型清單代表可評估的方法，不代表已具完整經濟模型求解器。
5. **模型選擇與適用性檢查**：先定義目標變數、預測期、地區、樣本區間及可用資訊集，再根據平穩性、資料缺口、樣本量、斷點、外生衝擊、模型可識別性及計算成本篩選方法；與季節性 naive／random walk、簡單計量基準比較，不盲目套用複雜模型。
6. **可重現估計與數值驗證**：計量估計、擬合、變數轉換、區間估計、情境比較與圖表，由可信確定性程式與經驗證統計套件執行。保存公式、程式與工具版本、原始數據、參數、隨機種子（適用時）、模型診斷、結果文件與數值單位。
7. **預測及不確定性**：提供基準／樂觀／悲觀（或明確界定的其他情境）及關鍵假設、敏感度、可驗證的預測區間；進行 rolling／expanding-window out-of-sample backtesting，避免 look-ahead leakage。評估 MAE／RMSE、方向準確率、區間覆蓋率與校準情形。不能把模型預測當成已發生事實。
8. **多學派實證驗證（D）**：同一政策議題可用不同機制提出替代假設，對照實際數據、識別限制和可靠研究；明確區分 correlation、structural interpretation 和 credible causal evidence。異質結果必須保留，不能強行合成單一確定答案。
9. **跨經濟體傳導分析**：對利率、匯率、通膨、信用、資產價格、產業鏈、財政與貿易政策，追蹤台灣、美國、中國及其他關聯經濟體的時間差、外生假設及衝擊機制；必要時連結管理與企業現金流，但不得從宏觀情境直接推斷單一公司的確定獲利。
10. **小模型工作分工**：October Core 負責題目拆解、方法選擇、來源需求和摘要解釋；RAG 存理論與出處；經濟計量／確定性工具負責估計與重算；Verifier 核對來源、公式、資料版本與執行證據。複雜需求只在 Q02 授權與 Q05 資源限制下升級較高容量節點。實際執行遵循 Q11–Q15 的核准模板、工具安全、資料契約與 DAG 調度。
11. **回答品質與限制**：簡易概念解釋可以走 Fast Path；政策、預測與經濟研究採 Verified／Deep Path，必要時交叉查證或請 Merlin 精準回問。專業成果標示「觀測」「估計」「假設」「預測」「推論」「未驗證」等不同層次，不可捏造估計係數、P 值或引用。
12. **實作狀態**：本題是使用者確認的架構與訓練目標，**不代表** October 已完成經濟模型權重訓練、已連上宏觀數據 API、已擁有經認證的 DSGE／VAR 求解器或已在專業 benchmark 達成大型模型水準。

### 驗收目標（尚未完成）

- 使用有歷史發行版本的台灣／美國／中國數據，對通膨、匯率或產出等問題執行至少一種簡單基準與一種可重現計量模型，進行樣本外驗證、區間覆蓋率及來源核對。

- 對「利率、匯率、出口、企業投資」建立多學派機制比較與結構化傳導圖，區分觀察與不可識別的因果推斷。

## Q17 / 50 — 全方位企業決策系統（Strategy × Analytics × Optimization × Evaluation）

**決策：D — 全方位企業決策系統。由使用者於 2026-10-20 正式確認。**

使用者原始決策：「整合經典管理學、數據驅動經營、數學最佳化、策略方案比較、KPI追蹤與改善效果驗證。」

### 綜合定位與工作契約

1. **四層管理能力整合**：Strategy（企業定位、產業結構與競爭策略）→ Analytics（營運／財務數據與根因診斷）→ Optimization（作業研究、資源配置、可行方案比較）→ Evaluation（KPI 追蹤、因果效果評估、迭代改善）。October 必須根據任務和資料成熟度選擇適用層次，而非每次一律產生四套內容。
2. **管理理論可追溯**：以 Porter 五力、價值鏈、SWOT／TOWS、PESTEL、資源基礎觀點、動態能力、平衡計分卡、目標管理、組織激勵與營運管理等作為工具箱；應揭露框架的假設與局限，避免以模板化理論名稱取代具體事實。
3. **企業財務及營運診斷**：視產業與資料情況建立 revenue bridge、成本結構、毛利／貢獻毛利、營益率／淨利率、自由現金流與現金轉換週期、應收存貨應付天數、產能利用率、品質／良率、顧客留存、CAC、LTV、流失、客單價、回購、員工生產率等 KPI；指標口徑及來源要明確，不可混合不同期間或不相容母數。
4. **結構化根因分析**：辨識「營收增加但淨利率下跌」可能源自售價／產品組合、材料與人工成本、固定費用增長、折舊、折扣、退貨、一次性項目、財務費用或會計口徑變動。先進行可重現的數量／價格／組合等分解與單位經濟驗證，區分相關和真正因果；資訊不足時由 Merlin 精準詢問。
5. **經營模型與情境模擬**：建立 unit economics、損益兩平、現金流預測、營運資金需求、價格彈性假設、規模經濟、客群／通路利潤及不確定性情境。將 Q16 宏觀利率、匯率、需求與通膨情境轉成可追溯假設，而不是直接假定宏觀模型結果會一對一反映在單家公司。
6. **數學最佳化**：針對具可信輸入與清楚約束的題目選用線性／整數規劃、排班、存貨 EOQ 或補貨政策、預算配置、產能／排程最佳化、蒙地卡羅及多準則決策；由可信求解器／確定性工具輸出結果，檢查約束可行性、敏感度及最佳化目標。若資料不足，提供可檢驗的候選方案而非偽造「最優解」。
7. **多方案決策比較**：對每個策略候選清楚列出適用假設、成本、所需人力／資本、預期 KPI 變化、不確定性、機會成本、執行風險、回收期與可逆性；可依使用者定義的權重排序，但不能擅自以模型偏好替代企業經營者目標。
8. **落地與執行邊界**：經核准的工作流程可生成計畫、里程碑、責任人、KPI 定義、儀表板及管理報表；實際修改員工排班、採購、售價、對外行銷、薪資或金流，都須先由 Detroit 檢查租戶授權與 Q04、Q06、Q12、Q13 的相應核准條件，不能從分析建議直接推定有操作權限。
9. **效果驗證與持續改善**：為方案設定執行前的基準期間、成功門檻、領先／落後指標、停損條件與回顧頻率；能實施時使用 A/B test、差異中之差、分期對照或中斷時間序列等方法檢查干預效果，並註明樣本、選擇偏差、季節性和外部衝擊造成的歸因限制。

## Q18 / 50 — 整合式專業財務分析引擎（Accounting × Financial Modeling × Valuation × Risk）

**決策：D — 整合式專業財務分析引擎。由使用者於 2026-10-20 正式確認。**

使用者原始決策：「融合財務會計與報表勾稽、企業財務及價值評估、三大財報連動與現金流預測、量化風險和壓力測試；以確定性計算及獨立驗證確保結果可重現、可稽核。」

### 專業能力與資料契約

1. **完整的五層分析流程**：Accounting（會計準則與報表勾稽）→ Modeling（歷史調整與三表連動）→ Valuation（投資評估與企業價值）→ Risk（不確定性、流動性、信用與壓力測試）→ Independent Verification（來源、會計恆等式、公式、輸出、執行證據）。October 按照題目深度及資料充足度套用必要流程，不因模板完整就自動產生沒有依據的估值。
2. **會計準則適用性**：依適用法域、企業報導主體、會計年度、報導版本與政策，檢查 IFRS／經我國認可的 IFRS（TIFRS）／US GAAP 的差異與適用期間。辨識認列、衡量、攤銷、減損、租賃、收入、金融工具與或有負債等重要會計議題；法規／準則時效性須由經核實的來源確認，不能用過時記憶替代。
3. **來源追溯與資料品質**：接受年報、財報附註、試算表、授權 ERP 匯出或其他明確資料源；依 Q14 使用版本化 JSON Schema／Artifact refs 保留報告年度、期別、幣別、量綱、合併／個別、審計狀態、發布／重編版本及原始頁碼或欄位。沒有實際讀取資料時不能宣稱已完成查核。
4. **財報勾稽與異常偵測**：檢查 Assets = Liabilities + Equity、現金期初期末變化、CFO／CFI／CFF 與現金變化勾稽、EPS 與股份數、損益至營運現金流、營運資金及各期橋接。對一次性利益、收入提前認列、資本化、現金轉換率、應收與存貨天數等設立風險旗標；異常是診斷線索，不可直接宣稱舞弊或已完成法定審計。
5. **三表連動模型**：透過損益表、資產負債表與現金流量表建立可追溯 driver-based 預測，涵蓋收入／毛利、營業費用、折舊攤銷、資本支出、營運資金、融資／利息、所得稅及現金結存。現金／債務循環引用須有明確解法與收斂驗證；提供歷史值、預測值及假設欄位，禁止任意硬塞平衡差額。
6. **估值與企業財務**：依企業形態與資料適用性選擇 DCF（FCFF／WACC 或 FCFE／股權成本）、股利折現、相對估值（例如 EV／EBITDA、P/E）及資本預算 NPV／IRR／回收期；ROIC、投入資本、槓桿及 WACC 稅盾應有一致定義，處理企業價值與股權價值、淨負債、少數股權及非營運資產的橋接。估值方法適用條件不滿足時明確限制結論。
7. **現金流與償債能力**：對基準、保守與衝擊情境預測自由現金流、營運資金缺口、最低現金餘額、利息保障倍數、DSCR／負債到期結構、再融資需要與契約限制。確認觀測期間、報表／現金流口徑及折現率一致性，不把會計獲利等同可動用現金。
8. **量化風險與壓力測試**：對營收、毛利率、資本支出、折現率、匯率、利率、原材料及收款週期做敏感度、損益兩平、情境／壓力測試；有足夠資料時可執行 Monte Carlo，揭露分布、相關性、樣本數、隨機種子及尾部假設。模型輸出的概率不是客觀確定性，不能把任意選定的分布假設當成觀測事實。
9. **獨立確定性計算與驗證**：所有重要數值交由受核准計算引擎／試算表公式運算，Verifier 獨立重算會計恆等式、FCFF／FCFE、WACC、DCF 終值及折現、NPV／IRR、流動性風險，檢查單位、精度與時間基準。若使用蒙地卡羅，須保存輸入、種子、程式／套件版本與產出，不讓語言模型捏造數值結果。
10. **專業分析工作流程**：October Core 理解問題與選擇經核准的財金模板；CREAM／GridCraft 或其他合法求解器承擔三表、估值及數值運算；Scout 只取得已授權且可核對的公開資料；Orchestra／WordCraft／DeckCraft 製作可引用成果；Detroit 依 Q11–Q15 提供權限、工具調度、Schema、Artifact Store 與持久化檢查點；LUCA 記錄錯誤和驗證結果。
11. **決策呈現**：分析結果至少應在適用情況下區分「已觀測財報事實」「會計判斷／調整」「估計參數」「預測情境」「風險限制」「可供使用者評估的選項」；顯示關鍵假設對企業價值的敏感度，不把單點合理價格當作無不確定性的結論。對不具足夠資料的個案，先標記缺口，必要時由 Merlin 精準回問。
12. **執行與資格界線**：財務資料讀取、投資建議、交易、正式更改帳務或報表提交，須遵守租戶身分、資料隱私、權限和需人工核准的高影響操作政策。系統提供輔助分析，不具有法定會計師簽證、審計或保證資格，亦不得宣稱已替代必要的專業判斷。
13. **規格與現況分離**：本題是確認未來整合式財務引擎的產品設計；不能從 GitHub 決策文件推論已建立可靠三表自動求解器、法規即時更新服務、完整企業估值部署或財務風險模型的獨立認證。

### 驗收測試（尚未完成正式實作）

- 以標準合成三大財報與帶附註／重編版本的案例，驗證會計等式、三表連動、期初期末現金及各年度財務比率的可重現性。

## Q19 / 50 — 整合式專業精算引擎（Life & Health × Non-Life × Stochastic Risk × ALM × IFRS 17）

**決策：D — 整合式專業精算引擎。使用者於 2026-10-21 正式確認。**

使用者原始決策：「結合壽險健康險、產險、保險定價與準備金、隨機精算、ALM、尾端風險與資本模型，納入 IFRS 17 和適用監理框架，使用確定性計算、獨立驗證及可重現模型測試。」

### 精算架構與專業執行契約

1. **完整專業範疇**：整合壽險與健康險精算、財產與責任保險精算、隨機模型、資產負債管理、保險財報計量、監理資本及企業風險管理（ERM）。October Core 負責界定問題、選擇合格的核准工作模板、組織證據及解釋限制；重要數值由確定性／統計引擎與獨立 Verifier 求解，不得靠 LLM 猜值。
2. **壽險與健康險**：建立生命表、死亡率／生存率、死亡改善、罹病率、發病／失能／康復轉移、退保率、費用率、保單期間與保障條件的版控模型。支援生命年金、保障現值、保費、準備金與負債現金流估算；明確保留年齡、性別／適用分群、投保年月、折現假設、給付時點及曝險基礎。公平性、合法可用特徵與資料保護依適用法域審核，不預設所有特徵都可用於實務定價。
3. **產險與理賠準備金**：納入 frequency–severity、集合理賠分布、理賠通膨與巨災情境，以及 Chain Ladder、Bornhuetter–Ferguson、Mack 等適用方法；管理事故／報案／支付期間及 development triangle，釐清已報未結、IBNR 和最終損失預測，檢查尾端因子、理賠資料截尾、暴露量及參數不確定性。
4. **定價與準備金分開治理**：純保費、附加費、費用、佣金、利潤與保險負債計量須有獨立模型版本、假設、法規界線和重算憑證。定價最適值不能直接視為法定或會計準備金，且不能從單一情境的「合理保費」推斷可在真實市場核准推出商品。
5. **IFRS 17 與適用監理**：納入 GMM／BBA、PAA、VFA 等適用模型的現金流履約估計、折現、風險調整、合約服務邊際（CSM）、虧損性合約、保險收入與負債變動調節需求；依報導法域與生效日取得可驗證的 IFRS 17／在地認可準則及監理版本。財務會計計量、法定精算準備金與清償能力資本是**不同目的與口徑**，不得混為一談；IFRS 17 並不是資本適足制度本身。
6. **隨機模型與精算統計**：在適用且資料足夠時使用生存分析、多狀態馬可夫模型、廣義線性模型、集合理賠、蒙地卡羅、隨機利率、信用與市場風險情境；核對模型識別條件、資料不確定性、厚尾、依賴結構與校準方法。所有機率、信賴區間與風險指標都明示模型與假設，不把模擬樣本當作真實觀測。
7. **資產負債管理（ALM）**：連動 Q18 的企業財務與保險負債現金流，分析資產與負債久期、凸性、現金流缺口、利率敏感度、再投資風險、流動性、保單選擇權、保證利率及必要的避險情境。不得只比較總資產與總負債金額就宣稱 ALM 風險充分管理。
8. **尾端風險與資本適足**：依明確定義的損失分布及時間範圍計算 VaR、TVaR／Expected Shortfall、壓力損失、再保險保護與資本緩衝，記錄信心水準、分布尾端、風險因子依賴和風險聚合方式。實際監理資本、清償能力及申報義務須按適用司法管轄區的當期規範與必要專業審核確認，不捏造監理認證。
9. **精算引擎與模型風險治理**：資料 → 計量假設 → 決定性算式／隨機抽樣 → 保費／準備金／負債及資本 → 獨立驗證 → 專業解釋。模型登記簿保留 model_id、版本、適用產品、資料來源／資料時點、模型文件、精算假設、參數、隨機種子、執行環境、輸出 hash、已知限制與核准狀態。避免使用者前端直接修改未經核准的生產計量模型。
10. **獨立驗證及回溯測試**：由與主要求解器分離的 Verifier 檢查生命表恆等式、保費／準備金現值、現金流調節、三角形資料、IFRS 17 roll-forward、ALM 現金缺口、VaR／TVaR 與情境壓測；模擬結果需有固定種子與誤差容忍區間。進行樣本外校準、經驗分析（actual vs expected）、模型漂移檢測，避免訓練／驗證資料洩漏。
11. **安全與私有資料**：醫療理賠、健康、身分、保單和財務資料需按明確目的、用戶同意、租戶／角色權限、保留期限與資料所在地政策處理。未授權資料不可流向朋友節點、共用模型訓練資料或雲端；隱私限制優先於運算效能。個人健康資料及保費歧視風險不得由模型自行決定政策合法性。
12. **October／Detroit 執行分工**：October Core 提出精算任務與核准模板選擇；適用的專業模型、RAG 與 deterministic calculators／統計套件負責實際計算；Detroit、CREAM／GridCraft、Orchestra 依 Q11–Q15 進行已核准的工具調用、JSON Schema／Artifact 交換、DAG 調度、結果與成本記錄；LUCA 回饋模擬收斂、錯誤率及異常；高風險發布、商品定價或監理用途需通過 Ceres／可信後端的核准。
13. **資格及實作邊界**：此規格不表示 October 擁有精算師執業資格或可取代法定精算簽證、商品審查、責任準備金簽認或監理申報；也不代表目前已實作完整的 IFRS 17 精算子帳、利率隨機模型或保險清償能力求解器。未執行工具、未取得有效資料和未完成審核時必須明說。

### 驗收測試（尚未完成正式實作）

- 使用合成生命表／健康險多狀態資料，驗證生存概率與保費／給付現值、準備金、折現及現金流時點，與獨立參考程式比較。

## Q23 / 50 — 多模態混合解析＋交叉驗證（Document Native Parsers × Retina × OCR × Verifier）

**決策：D — 多模態混合解析及交叉驗證。由使用者於 2026-10-21 正式確認。**

使用者原始決策：「依文件類型選擇原生解析、表格及公式處理、Retina視覺辨識與必要OCR，輸出有JSON Schema及頁面/座標來源參照的結構化內容，對關鍵數據與圖表由Verifier獨立驗證，並以Detroit Artifact Store保存版本與證據；遵守離線、隱私與節點授權限制。」

### 多模態文件理解架構

1. **路由優先、能力確知**：October 只決定需讀取哪些內容，Detroit Document Router 根據檔案 MIME／magic bytes、頁數、原生文字層、可用原生表格、解析工具狀態、資源成本及授權決定實際解析路徑；檢測不得只信任副檔名。Retina 未安裝／無法辨識圖片時必須明確回報，不可讓純文字模型假裝看過圖片。
2. **原生解析為預設途徑**：具文字層的 PDF、DOCX、XLSX、PPTX 及結構化資料以原生解析器提取內容、樣式／章節結構、頁碼、投影片、工作表、儲存格地址、公式與資料型別。對 HTML、嵌入圖形、註解及隱藏欄列保留必要上下文；可直接提取者不應先影像化再做低精度 OCR。
3. **表格結構與單位辨識**：保留 row/column、合併儲存格、跨頁表格、欄位階層、表頭、腳註、貨幣、數字格式、正負號、倍率（元／千元／百萬元）、年度／季度、百分比、缺失值與資料來源。表格內容要能回指原始儲存格或 PDF 頁面範圍；不得把空白自動解讀為零，或把格式化值錯認為數值。
4. **公式與圖表理解**：數學式保留原始符號、上下標、單位、定義範圍與條件；試算表保存公式文字、依賴、計算快取與重算狀態，對巨集或外部連結採不可信處理。圖表識別座標軸、尺度、對數軸、圖例、分類、圖說、錯誤棒與資料系列；有原始底層數據優先直接使用，僅從影像估數值需標為估計，不得憑視覺讀出不具精度的精確數字。
5. **Retina 視覺模型按需補強**：對圖片、文件版面、圖示、醫學影像的非診斷性說明或需要視覺關係的內容，使用已部署且驗證可用的 Retina。Retina 結果作為結構化候選與原始證據並存；若失敗、置信度不足或與原生資料矛盾，啟動核對、局部重解析或標記未確認，不得把模型敘述直接當成原始事實。
6. **OCR 最後才用**：對掃描頁、影像文字或無文字層且無更可靠原生來源的區塊，經過頁面取樣、區域偵測和授權檢查後使用適用語言 OCR。避免逐頁無條件 OCR、過度渲染高解析度與無上限影像處理。無可用 OCR 或語言不支援時需回報限制，不能編造內容。
7. **Typed Extraction Envelope**：經 Q14 JSON Schema 輸出 document_id、artifact_id、source_hash、parser_id／version、source_type、page／slide／sheet、bounding_box 或 cell_range、reading_order、block_type（text/table/formula/chart/image）、extracted_payload、units、evidence_ref、provenance、validation_state、uncertainty、tenant_id／access_scope 等欄位。對掃描圖的頁碼、區域、圖表元素建立可重新顯示及人工覆核的定位參照。
8. **來源定位與資料版本**：Document Router 生成帶固定來源雜湊的可引用片段，必要時保存原始頁縮圖／裁切區域的 artifact（依來源授權），避免文件再次上傳後頁碼偏移。解析後結構、原始檔案與數值驗證證據均經 Q14 Artifact Store 版本化，並由 Q21 快取、資料版本與引用存續政策管理。
9. **獨立交叉驗證**：Verifier 不只比較兩個模型是否說法相同，而是核對原始表格／儲存格、各合計與子項、會計恆等式、公式可重算性、日期／單位／符號，並保留不一致、缺值或低可信欄位。對關鍵財務／精算／醫療數值若無充分原始證據，不得輸出貌似確定的結果。
10. **多頁長文件與低資源處理**：對大型報告分段、按需求提取、先讀目錄與結構，再按 Q22 混合檢索拉取相關區塊；只將摘要及引用傳給小模型。依 Q05／Q15 的資源限制分片、限流、快取及按需啟用 Retina，不讓本地手機因逐頁 GPU 視覺推論而耗盡記憶體或電池。
11. **不可信檔案安全**：對壓縮炸彈、PDF 惡意附件、Office 巨集、外部資料連結、內嵌腳本、追蹤資源、影像 EXIF、可疑 OCR 提示注入等採 sandbox、檔案大小／頁數／解碼時間上限及最小權限；文件內容僅屬待分析資料，不能充當 Detroit 系統指令或授權。
12. **資料私密性與節點權限**：解析、暫存、嵌入、圖像裁切、模型呼叫與下游交接均尊重用戶授權、租戶隔離、私密模式、Q02 節點資料所在地、Q13 工具安裝安全及 Q21 來源保留條款。雲端 OCR／VLM 未明確獲准不可自動取得敏感檔案；不能因某節點有 GPU 即傳送醫療或財務敏感資料。
13. **Detroit 生態協作與未完成狀態**：Retina 提供視覺能力、CREAM／GridCraft 處理已驗證數值及試算表、Orchestra／WordCraft 製作成果、Q22 取得章節與引用、LUCA 追蹤解析偏誤及故障。規格不代表 Retina 已經修復或可用、OCR 已安裝、所有格式都支援，亦不代表已讀取或解析使用者實際上傳的某份文件；成功狀態必須來自真實工具與驗證記錄。

7. **Telegram 互動工作流**：本人可透過 Telegram 對話或按鈕使用「檢查錯誤／設定範圍／開始修補／查看 Diff／執行測試／建立 PR／查看失敗／暫停／取消／核准高風險變更」。每次動作需顯示 repo、分支、作業 ID、影響範圍、測試結果、風險與所需權限；按鈕回傳由後端驗證，不由模型直接相信 Telegram 文字中的權限宣稱。
8. **人工審查與合併／部署界線**：PR 是交付物，不是已核准合併。**只有經本人 Telegram 明確批准**才可啟動合併、正式部署、權限變更、可能破壞資料的修復或回滾；另須遵守 GitHub Branch Protection、必需 CI 與後端政策。若 GitHub 自身沒有允許的權限，Telegram 核准也不能繞過。
9. **可觀測與真實回報**：Detroit 保留 task_id、批准者、Telegram action ID、repo／base SHA／head SHA、每階段狀態、測試輸出、失敗原因、PR URL、運算節點及 ArtifactRefs；LUCA 提供不洩漏秘密的診斷摘要。不得在工具未執行或 PR 未實際建立時聲稱「已提交」、「修復成功」或「已部署」。
10. **與既有架構分工**：October 負責規劃與程式工程決策；Diana 依 Q11–Q13 選用核准的除錯／修改／測試模板；Detroit Executor 實際執行並 enforce scope；LUCA 提供錯誤與回饋；Quirinus 對權限與安全風險提供檢查；Ceres 作為唯一 Owner Control Plane；Slime 僅可在 Q02／Q15 允許節點上執行。不能把開發 Agent 暴露成一般使用者可操控的公開功能。
11. **與 D 方案的清楚區別**：本題沒有另行採納 D 作為整體「驗證驅動的完整自主工程系統」產品決策。為實施 B＋C 所必須的基本沙盒、權限閘門、測試證據與 PR 審核是安全必要條件；高階安全紅隊、自動部署治理、效能基準策略等可於後續議題獨立選擇，不偷偷視為本題已決定全部進階功能。
12. **狀態聲明**：此為 October 未來產品規格與專屬 Telegram 管控原則，**不代表**目前已建立專用開發代理人、Telegram 白名單驗證、可靠分支編輯／測試／PR 流程，或已取得倉庫寫入及正式部署權限。必須透過實際程式、權限測試及部署證據驗收。

## Q26 / 50 — D：分層式自主資安防護系統（October × Quirinus × Ceres Telegram）

**決策：D — 分層式自主資安防護系統。使用者於 2026-10-21 正式確認。**

使用者原始決策：「採分層式自主資安防護系統，整合漏洞監測、風險評估、依賴與機密掃描、受控修補、隔離測試及 PR 驗證；October 與 Quirinus 協作，只有本人能透過 Ceres Telegram 控制與核准高風險修改、合併及部署。」

### 信任邊界與威脅模型

1. **系統角色與最小權限**：October 負責理解風險、分類事件、計畫與審核工作流；Quirinus 執行受核准的依賴、原始碼、機密、組態及安全政策掃描與發現歸納；Detroit 的可信 Executor 實際執行隔離命令、記錄證據和強制權限；Ceres Telegram 是**唯一 Owner 控制平面**。原始碼／工具輸出皆視為不可信資料，不得自動轉化成系統指令、程式碼寫入權或部署許可。
2. **所有控制僅限本人 Telegram**：依 Q25 的 Owner Telegram user_id、受限私聊 chat_id、後端驗證、短時效一次性 callback nonce／action token 與審計紀錄，授權資安掃描的執行範圍、觸發受控修補、建立 PR、合併、部署、回滾、擴張網路掃描許可或新增權限。一般 Vanilla 前端、公開模型 API、群組、朋友 Slime 節點或其他管理員都不可操作。僅收到文字訊息「我是 Owner」不能繞過可信平台身分驗證。
3. **防護資產與範圍**：以 Owner 明確指定的 Vanilla/Detroit/Ceres/Slime 程式庫、部署環境、相依套件、映像、IaC、CI/CD、API 權限及服務設定為保護範圍；維護核准 target manifest（repo_id、branch、environment、allowed_paths、approved_hosts、allowed_scanners、budget、有效期限）。未列入範圍的第三方網站、雲端服務、朋友主機及網段不得掃描或進行主動測試。
4. **分層檢測**：分離軟體組成分析 SCA（依賴版本、已知漏洞、授權與 SBOM）、靜態程式碼掃描 SAST、秘密／金鑰外洩檢查、GitHub Actions 和 CI 權限審核、Docker/容器映像及 Infrastructure-as-Code 設定檢查、供應鏈 provenance／簽章檢查。動態測試 DAST 或攻擊模擬只允許在明確核准的隔離環境與目標內進行，預設不得碰正式生產服務。
5. **漏洞證據與去重**：保留 advisory_id／CVE（若真實存在）、套件與受影響版本、鎖定檔／SBOM 證據、修復版本、掃描器版本、資產上下文及引用來源時間；Quirinus 依實際受影響程式與可達性去重、排除誤報與留存處置原因。若未核對 advisory 或適用版本，不可編造 CVE、已利用情況或「沒有漏洞」的保證。
6. **風險分級**：依漏洞嚴重度、資產暴露、可被利用證據、資料敏感度、權限、攻擊面、業務衝擊、修復回歸風險與補償控制分類 T0–T3；CVSS 或其他分數是參考，不代替個案風險判定。T0/T1 可自動執行**預先授權的唯讀掃描與低風險診斷**；T2/T3 及任何會改程式或權限的動作，依 Q25 範圍和 Telegram 授權閘門控制。
7. **受控修補與分支隔離**：在 Owner 先批准的工作範圍內，可為漏洞準備相依升版、組態收斂、最小補丁與回歸測試，並在隔離 branch／worktree 上產生 diff、SBOM 改變、lockfile 差異、PR 草稿或經授權 PR；預設不得直接提交 main、改正式金鑰、撤除安全控制或執行正式資料庫 migration。
8. **修補驗證**：獨立執行 build、單元／整合測試、相關安全測試、靜態檢查、原漏洞再掃描、相依完整性／授權檢查及必要效能回歸；Verifier 核查掃描器真實回報、修補後受影響版本與安全政策，測試未通過則保留 failed/blocked，不可把「建立 PR」等同「漏洞已修復」。
9. **高風險操作必須本人明確核准**：PR 合併、正式部署／回滾、刪改資料、重置權限、機密輪替、變更認證規則、開啟高權限掃描／網路測試、關閉安全掃描和擴大監測目標，必須先有 Telegram 發出與特定 repo／commit／target／環境綁定的單次授權，再通過 GitHub branch protection、CI 及可信後端 policy。即使 Owner 核准，也不得繞過不可關閉的安全政策或平台原有權限。
10. **可見、可拒絕、可中止**：Ceres 提供風險摘要、掃描報告、受影響依賴、Diff、測試狀態、修補候選、PR 連結、批准／拒絕／取消選項。高風險確認須顯示具體影響及回退方案；取消要防止新的副作用步驟，已產生的不可逆影響需如實回報。
11. **通報和應變**：根據 Owner 所核准事件類型，在 Ceres Telegram 提交風險摘要和必要優先順序，避免轉送完整憑證或高敏感資料；涉及緊急曝險而不適合等待修復時，先提出隔離、暫時限制及人工操作建議，任何真實停機、憑證撤銷或變更正式環境仍需既定授權。長期監測須以真正部署的常駐服務／排程為前提，不能宣稱單次聊天能持續監控。
12. **機密資訊保護**：禁止在模型提示、公開日誌、PR diff、Telegram 訊息和第三方掃描服務中放入明文 secrets；掃描發現時只留遮罩後摘要、檔案定位與風險類型。若曾暴露秘密，依 Owner 授權執行輪替、撤銷、影響查核與 Git 歷史清理評估，不能只刪除目前檔案就聲稱機密已安全。
13. **供應鏈與來源安全**：核對套件來源、授權、版本鎖定、CI workflow 權限和 SBOM；第三方掃描器或安全外掛依 Q13 須經可信 Adapter、簽章／權限與執行環境檢查，不可以「資安工具」名義取得主機 root 或 Owner 的 GitHub 金鑰。掃描輸出、issue、README 及任意外部內容不得被當成優先於系統政策的指令。
14. **可稽核任務鏈**：每次作業保存 task_id、scan_target、scope_version、scanner/tool/version、risk tier、evidence refs、owner_telegram_action、approval token 消耗狀態、base/head commit、測試證據、PR 狀態及最終結論；保留必要最小化的不可竄改稽核證據，並遵 Q14 Artifact Store／Q21 授權與資料保留政策。LUCA 只追蹤脫敏指標、誤報率、檢測延遲、修復驗證狀況和成本。
15. **模型與實際部署狀態分離**：本題定義受控的自主資安設計，不表示 Quirinus 已具所有掃描器、已在正式環境接通實時 CVE 通報、Telegram Owner policy 已完整強制執行，也不表示任何掃描、PR、合併或部署已完成。所有成功狀態需來自真實工具執行與後端回傳。
